Normalizing predicted funding rates to one interval

Why I convert every venue to % per 8 hours before averaging, and drop stale rates instead of counting them.

Predicted funding is one of the first numbers I look at when a perpetual market starts to move. It says which side is paying, roughly how much, and whether that pressure is building or fading before the next settlement. The trouble starts when you want one number for the whole market instead of one per venue.

The Coinalyze API returns predicted funding rates per venue, but no aggregate. Coinalyze does show an aggregate, as a chart on coinalyze.net, and that chart lags behind the API. So I built the predicted funding aggregator to compute the aggregate myself and stream it as it changes. Most of the work turned out to be deciding what “the same number” means across ten venues.

Rates arrive in different units

A funding rate only means something together with its interval. Some venues settle funding every hour, others every 8 hours. A predicted rate of 0.01% on an hourly venue and 0.01% on an 8-hour venue look identical in a JSON response, but over the same 8 hours the first one is paid eight times.

If you average the raw values, the hourly venues are quietly under-weighted by a factor of eight. The average still moves, still looks plausible on a chart, and is wrong. Nothing errors, nothing logs a warning, and the mistake only shows up when someone compares the number with a venue they know well.

Pick one interval and convert everything to it

The fix is unglamorous: choose a reference interval and convert every rate to it before doing anything else. I use % per 8 hours because it’s the convention most traders already read funding in, so the output needs no explanation.

The conversion is a single multiplication, by the number of the venue’s intervals that fit into 8 hours:

Keep the interval next to the rate

The conversion is only as good as the interval you feed it. Hard-coding each venue’s interval means trusting that it never changes, so the interval travels with every rate as data, and the conversion happens in exactly one place:

// One rate as the aggregator sees it.
type VenueRate = {
  venue: string;
  rate: number;          // % per funding interval
  intervalHours: number; // travels with the rate, never hard-coded
  updatedAt: number;     // ms since epoch
};

export function toPer8h(r: VenueRate) {
  return r.rate * (8 / r.intervalHours);
}

export function fresh(rates: VenueRate[], now: number, maxAgeMs: number) {
  return rates.filter((r) => now - r.updatedAt <= maxAgeMs);
}

export function averages(rates: VenueRate[], oi: Map<string, number>) {
  const per8h = rates.map(toPer8h);
  const simple = per8h.reduce((sum, v) => sum + v, 0) / per8h.length;

  const w = rates.map((r) => oi.get(r.venue) ?? 0);
  const total = w.reduce((sum, x) => sum + x, 0);
  const weighted = per8h.reduce((sum, v, i) => sum + v * w[i], 0) / total;

  return { simple, weighted };
}

Everything downstream of toPer8h works in a single unit. That includes the chart history kept in SQLite, so what is stored is already in the unit that is displayed, and a restart never has to guess which unit an old point was written in.

A stale rate is not a rate

The second problem is time. Venues update their predicted rate at different cadences, and now and then one stops updating for a while. The API still returns the last value it has. If the aggregator treats that value as current, the average carries a number that describes the past.

A rate that has stopped updating isn’t a small rate or a zero rate. It’s a missing value, and the honest thing to do with a missing value is to leave it out.

So each rate carries the time it was last updated, and anything older than a configured maximum age is dropped before averaging. Dropping is a deliberate choice. Filling the gap with the previous value, or with zero, both produce a smooth line, and both hide the fact that one venue is no longer contributing.

What dropping costs

Dropping a venue shifts the average, because the set of venues behind it has changed. That shift is information, not noise, so the dashboard shows the per-venue breakdown right next to both averages. When the aggregate jumps, the breakdown shows at a glance whether the market moved or a venue fell out.

Choosing the maximum age

There is no universal right value for the maximum age. Set it too short, and venues that simply update on a slower rhythm drop out of the average even while their value is still current. Set it too long, and a venue that has gone quiet keeps steering the number. It belongs in configuration rather than in code, so it can be tuned from what you observe of the venues without shipping a new release.

Two averages, two questions

Once every rate is fresh and in the same unit, there are still two reasonable ways to combine them, and they answer different questions.

  • The simple average gives each venue one vote. It answers: what is the typical venue predicting?
  • The open-interest-weighted average gives each venue a vote in proportion to its open interest.1 It answers: what is the money in the market predicting?

When the two agree, there is not much to say. When they diverge, the smaller venues and the venues that hold most of the open interest are pricing funding differently, and that gap is worth watching in its own right.

The service streams both over an authenticated WebSocket, so anything consuming it can pick the one that fits its question instead of having that choice made for it.

Checking it against the reference

An aggregate you can’t check is just another opaque number, which is exactly what I set out to avoid. The reference was the aggregate chart on coinalyze.net. I compared the two over 40 samples: every venue with an API rate landed within 5% of its expected ratio.

Within 5% is not the same as identical, and it isn’t meant to be. The two sides sample at slightly different moments, so small differences are expected. What the check rules out is the kind of error that matters: a wrong interval, a missing venue, or a stale value pulling the average somewhere it shouldn’t be.

The comparison also put a number on the original complaint. For ETH and SOL, the chart lagged the API by about 165 minutes. That is a long time in a market where some venues settle funding every hour.

If you build the same thing

  • Store the interval with the rate. Don’t infer it from the venue name.
  • Convert to one unit at the edge, before anything is averaged, stored or charted.
  • Drop stale values instead of filling them, and show which venues are behind the number.
  • Offer both averages and label them plainly.
  • Check the output against whatever reference people already trust, and write down how far apart the two are.

None of this is complicated. It is the kind of detail that decides whether an operations number can be trusted at 3 a.m., when nobody has time to wonder which unit it is in.

Footnotes

  1. Open interest is the value of positions still open on a venue. A venue with twice the open interest counts twice as much toward this average; the simple average ignores open interest entirely. ↩
